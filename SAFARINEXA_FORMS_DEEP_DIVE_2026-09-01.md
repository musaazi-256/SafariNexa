# SafariNexa forms deep dive — listing creation, rooms, reservations, images

**Date:** 1 September 2026 (follow-up to `SAFARINEXA_FORMS_AUDIT_REPORT_2026-09-01.md` from earlier today)
**Scope:** requested deeper trace on (1) new-listing creation forms, (2) room/accommodation creation, (3) the customer reservation journey end to end, (4) image upload logic, and (5) downstream/public-facing impact of the gaps already found this morning.
**Method:** four parallel deep-dives, each tracing data FORWARD from where a form saves it to every place it's later displayed, reported on, or interacted with — not just "does the form write correctly," but "does anyone ever see what was written, and does it stay consistent across every place it appears." Read-only; no code changed. This is prep for a fix pass, not the fix itself.

## Executive summary

The morning's audit found 3 bugs where forms lose data on write. This pass found a different, arguably more important class of problem: **data that writes correctly but then goes stale, is never read back, or is read inconsistently across the app** — plus one more genuine write-side bug (restaurant hours) and one real data-integrity hole (deleting a room type can erase which room a historic booking was for). The single most consequential finding is that **the accommodation booking widget shows less room detail than the card the customer just clicked** — bed type, features, and refund policy are visible on the room card but silently dropped before they reach the actual "Reserve" form.

Highest-priority new findings, in the order they'd surprise a real user:

1. **Restaurant opening hours never display for any business-created restaurant** — a genuine shape mismatch between what the form writes (`Json` as a plain string) and what the detail page expects (`{summary: string}`). Only seed-data restaurants show hours; every real one is silently blank.
2. **The room-selection widget drops most of the room's identity.** `RoomPreviewCard` (the browsing view) shows bed type, room features, refundability, and refund policy; `AccommodationReservationFields` (the actual booking widget, one scroll below) only knows the room's id/name/description/price/occupancy/breakfast. A customer choosing between two rooms with different bed configurations can no longer tell them apart at the point of booking.
3. **A deleted room type can silently erase which room a past booking was for.** `Booking.roomTypeId` is a live, non-snapshotted relation with Prisma's default `SetNull` behavior on an optional foreign key; the accommodation edit flow already deletes room types that have no bookings, and nothing stops a room type *with* bookings from later being deleted through some other path, at which point historic booking detail pages lose the room-and-add-ons section entirely.
4. **Two independent, disagreeing availability systems exist.** The customer-facing calendar computes "is this date booked" by counting live `Booking` rows itself; the actual booking transaction enforces capacity through a separate `Availability` table it upserts/decrements. They're never reconciled — the "N rooms left" badge shown while browsing is not the same number that governs whether checkout will actually succeed.
5. **Image uploads have no size, count, or type limit anywhere**, and are stored as raw base64 text directly in Postgres rows (confirming this morning's finding, now with scale numbers: ~10–65MB per listing's `images[]` column for 8–10 photos), and list-view queries (search, business's own listings table) fetch that entire blob for every row even though they only render one thumbnail.
6. **Business verification documents are written to the local filesystem** (`fs.writeFile` into `public/uploads`), which will not persist (or will outright fail) on typical serverless hosting — a real production risk specific to KYC documents, independent of the base64-in-Postgres problem affecting listing photos.
7. **A rejected or changes-needed business currently gets no reason why.** This morning's audit found admin's rejection-note field is hardcoded; this pass found the deeper problem — that field is never read back *anywhere*, not in the notification, not on the business's own verification status page, which shows a static "under review" message regardless of the real status. The net effect: rejection currently looks, to the business owner, identical to being ignored.

Everything else investigated — the description/logo/city-country gaps from this morning, admin role rigidity, and the guide-destination gap — traced out as genuinely harmless today, each for a specific, confirmed reason (no public page exists yet to expose it, a parallel clean field is used instead, or nothing in the code branches on it). Full detail below.

## 1. New listing creation — where does each field actually get seen?

Cards and search results (`listing-card.tsx`, `listing-row.tsx`) intentionally show only base `Listing` fields (title, city, price, cover photo, rating) — type-specific detail belongs on the detail page, and that's where it goes. All four listing types' detail pages render essentially every column their form collects, **except**:

- **Bug — Restaurant opening hours.** The business form's parser (`src/lib/business-listing-form.ts:140,147`) stores `openingHours` as a raw string in the `Json?` column. The detail page reads it as `(restaurant.openingHours as {summary?: string})?.summary` (`src/app/restaurants/[id]/page.tsx:49`) — which only resolves for seed data, written as `{summary: "..."}` (`prisma/seed.ts:1087`). A plain string is valid JSON, so it saves without error; `"a string".summary` is just `undefined`. Every real business's opening hours are invisible on their own restaurant page.
- **Dead data — `RestaurantProfile.acceptsReservationRequests`.** Collected, persisted, shown back in the edit form — never read on the public page, in search, or by any reservation logic. It currently does nothing.
- **Fake filtering.** Search's property-type, tour-type, duration, vehicle-type, cuisine, specialty, and amenities filters all do a plain substring match against listing `title`/`description` (`src/app/search/page.tsx:216-293`) instead of querying the real structured columns (`AccommodationListing.propertyType`, `TourListing.tourType`, `TransportOption.vehicleType`, `RestaurantProfile.cuisineType`, `AccommodationListing.amenities`) that the create form correctly saves. The data is right; the filter reading it isn't. (Guest-count/capacity filters, by contrast, do correctly query the real columns.)
- **No self-visibility.** A business's own listings table (`src/app/business/(portal)/listings/page.tsx`) shows only title/type/city/price/status — none of the type-specific detail they just entered is visible to them without opening the edit form. The same page's "Views this month"/"Bookings this month" figures are hardcoded literals, not derived from anything.
- **No admin listing detail.** There is no admin page that shows a single listing's fields at all — admin only ever sees title/type/status nested inside a business's profile page.
- **`Destination` is a closed catalog.** `destinationId` filtering itself works correctly end-to-end (confirmed fixed, matches the 31 August finding). But there is no create/edit UI for `Destination` anywhere — a business or admin can only attach a listing to a destination that was pre-seeded; new destinations can't be added through the product at all today.

## 2. Room/accommodation creation and the customer reservation journey

Tracing the full path from a business creating a room to a customer completing a stay:

- **Room browsing is complete; room booking is not.** `RoomPreviewCard` (the card shown while browsing) renders every `RoomType` column — bed type, bedrooms, room features, refundability/refund text, discount notice, breakfast, price. `AccommodationReservationFields` (the widget that actually adds the room to cart/checkout, one scroll below on the same page) only receives `id, name, description, images, priceMinor, maxOccupancy, breakfastIncluded, bookedDates` — bed type and features are simply never passed to it. The room's id does flow through correctly (via a `selectRoom` custom event), so the *booking* itself is for the right room — but the customer can no longer see what makes that room different from another at the moment they're choosing to reserve it.
- **Two parallel availability systems.** `getRoomTypeAvailability` (`src/lib/listings.ts:18-63`) — used by the customer-facing calendar — counts overlapping non-cancelled `Booking` rows and marks a date full once it hits `totalRooms`. Separately, `booking-service.ts`'s transaction enforces capacity through the `Availability` table (`tx.availability.upsert`, decrementing `remaining`). These are two independent calculations that are never reconciled against each other. The "We have N left" badge on the room card additionally just shows the static configured `totalRooms`, not either computed number — so a browsing customer sees one "remaining" figure, the calendar (if they open it) computes a second, and checkout enforces a third.
- **Pricing integrity is actually solid.** `validateAndReserveBookings` recomputes the charge fresh from the current `RoomType.priceMinor` inside the transaction and explicitly ignores whatever total the client submitted (`checkout/page.tsx:100` even comments `// Ignored on backend`) — so price tampering isn't possible, and a stale client price never gets charged. The one real gap: if a business changes a room's price between a customer adding it to cart and completing payment, the customer is charged the new price with no diff or confirmation shown anywhere — they only find out after paying.
- **Bug — single-item checkout has no error handling.** If a booking fails validation (e.g. the room sold out between page-load and submit), cart/multi-checkout at least shows the thrown message via `alert()`. Single-item checkout (`src/app/checkout/page.tsx`) has no try/catch around the same call, so the identical failure surfaces as a raw, uncaught Next.js error page instead of a readable message.
- **Data-integrity risk — room deletion can erase booking history.** `Booking.roomTypeId` is a live foreign key with no `onDelete` override, so Prisma's default is `SetNull`. The accommodation edit flow already deletes room-type rows that have zero bookings; nothing in the schema stops a room type *with* existing bookings from being deleted some other way (e.g. directly, or if that safety check is ever loosened), at which point every historic booking referencing it silently loses its room information — the "Room & add-ons" section disappears from the booking detail page entirely, because nothing snapshots the room's name/features at booking time the way `BookingAddOn` already does for add-ons.
- **Downstream visibility is thin and uneven.** Customer and business booking-detail pages show only `roomType.name` post-booking — none of the room's other attributes. **Admin has no booking detail page at all**, and its list query doesn't even fetch `roomType` or `addOns` — admin can see a price and a listing name for a booking, never what was actually booked. Add-ons, by contrast, are correctly snapshotted at booking time (`BookingAddOn`) and shown consistently on both customer and business detail pages — just not to admin, and not on any list/revenue view.

## 3. Image upload logic, end to end

- **No guardrails at all.** `src/components/ui/image-uploader.tsx` (the one real uploader in the app, used for listing photos and room photos) enforces no file size limit (the "up to 10MB" copy is decorative text only), no count cap on how many images can be added, and no real file-type check (`accept="image/*"` is just a picker hint, trivially bypassed) — any file becomes a base64 `data:` string appended to the array, no compression or resizing applied.
- **Where it's stored.** That base64 string is persisted directly into Postgres text columns — `Listing.coverImageUrl`, `Listing.images[]`, `RoomType.images[]`. At 1–5MB per photo and ~33% base64 inflation, a listing with 8–10 photos puts roughly **10–65MB into a single database row.**
- **It renders without crashing, but without benefit either.** Next.js 14.2's `<Image>` component auto-detects `data:`/`blob:` URIs and falls back to unoptimized rendering rather than erroring — so galleries and cards display fine, but every visitor downloads the full, uncompressed original with none of `next/image`'s resizing/optimization benefit. Several other spots (business dashboard, listings table, bookings table, revenue page) render the same base64 values through plain `<img>` tags instead.
- **List views over-fetch it.** Search (`src/app/search/page.tsx:173-176`), the shared listings helper backing the home/explore pages (`src/lib/listings.ts:111-113`), and the business's own listings table (`src/app/business/(portal)/listings/page.tsx:44`) all query listings with a bare `include`/no `select`, which pulls the *entire* `images[]` array into memory and over the wire even though every one of those views renders only the single `coverImageUrl` thumbnail.
- **Verification documents take a different, riskier path.** `src/lib/actions/verification.ts` writes uploaded KYC files with a real `fs.writeFile` into `public/uploads` — not base64-into-Postgres. That's the right instinct, but a local filesystem write does not reliably persist on typical serverless hosting (the working directory is ephemeral/read-only at runtime on platforms like Vercel), which is a real, independent production risk for exactly the documents that matter most for compliance.
- **Genuinely unused, confirmed harmless:** `BusinessProfile.logoUrl`/`coverImageUrl` and `Destination.heroImageUrl` still have zero form setters anywhere (extends this morning's finding) — but per §4 below, nothing public currently reads them either, so this is a missing-feature gap, not an active bug.

## 4. Downstream impact of this morning's findings

Re-checked whether the gaps found in the earlier `SAFARINEXA_FORMS_AUDIT_REPORT_2026-09-01.md` are actually visible to a real user today:

| Finding | Verdict | Why |
|---|---|---|
| Business description/logo never set at onboarding | **Harmless today, with a landmine underneath.** No public `/business/[slug]` profile page exists anywhere for a customer to see it missing. But Settings' description textarea uses its *placeholder text* as the field's `defaultValue` (`settings/page.tsx:96`) — if an owner submits the form without touching it, the literal placeholder ("We provide the best safari experiences in East Africa.") silently becomes their real, permanently-saved description. |
| `BusinessProfile.city` overloaded with a full address | **Harmless.** Search and all customer-facing city display actually use a separate, clean `Listing.city` field (a dedicated form input, defaults to "Kampala") — untouched by the overload. The overloaded field only ever appears as plain text on two admin-only pages; nothing filters or groups by it. |
| Admin verification notes hardcoded | **The visible problem is worse than "hardcoded."** The `reviewNotes` field isn't just always the same string — it's never read back anywhere at all. It's absent from the business-owner notification (which only states the new status) and the business's own verification page doesn't even select it from the DB, instead always showing a static "under review" message regardless of whether the real status is REJECTED or NEEDS_CHANGES. A rejected business today gets no reason and a UI that still claims they're pending. |
| Every admin invite hardcoded to Super Admin | **Fully inert.** Confirmed nothing anywhere in the codebase branches on `AdminUser.roleId`/`Role`/`Permission` — every active admin already has identical access regardless of role, so the missing role selector currently changes nothing behaviorally. |
| Guides missing `destinationId` | **Mostly harmless.** The "Destination specialist" badge people would assume is affected is actually driven by a separate, correctly-wired field (`Guide.specialization`) — not broken by this gap. Only a "Based near X" text line silently doesn't render; no destination page lists guides at all, so there's no broken filter either. |

## Consolidated fix priority (for the upcoming pass)

Roughly in order of how much real damage each does today:

1. Room-type edit data loss (found this morning) + room-deletion history loss (found this pass) — both corrupt or erase real `RoomType`/`Booking` data; fix together since they touch the same code paths.
2. Restaurant `openingHours` shape mismatch — a one-line fix (store/read the same shape) that currently blanks every real business's hours.
3. Reconcile the two availability systems, or at minimum make the "N left" badge and the calendar agree with what checkout will actually enforce.
4. Wire the room-selection widget to carry the full `RoomType` (or at least bed type + features) so the booking form matches the card the customer clicked.
5. Give single-item checkout the same error handling cart checkout already has.
6. Fix the Settings description placeholder-as-defaultValue landmine before it silently ships fake descriptions.
7. Give admin a real booking detail view (room + add-ons), and decide whether verification `reviewNotes` should actually reach the business owner — right now a rejection is indistinguishable from silence.
8. Image pipeline: add server-side size/count/type limits to `image-uploader.tsx` immediately (cheap, prevents active abuse); treat swapping base64-in-Postgres for real object storage, and moving verification uploads off local `fs`, as the larger pre-production item from this morning's report.
9. Everything else in this report (fake search filters, no admin listing detail, no `Destination` CRUD, business self-visibility) is a product-completeness gap rather than a bug — worth sequencing in, not urgent.
